## Two things I checked rather than assumed

**A silent write failure.** Creating a playlist with its schedule in the
same call returns HTTP 200 and a completely normal-looking playlist, with
`schedule_items: []`. AzuraCast drops the schedule on create and only saves
it on a follow-up `PUT`. I only caught it because I read the response back
instead of checking the status code. Had I not, the playlists would have had
no schedule at all, which does not mean "never plays". It means **plays
constantly, forever**, starting immediately.

**Whether the schedule would actually fire.** The obvious verification,
`GET /api/station/{id}/schedule`, returned an empty list no matter what date
range I gave it. Rather than guess, I read AzuraCast's own source: that
endpoint filters on `is_jingle = 0` because it feeds the listener-facing
calendar, and jingle playlists never appear in it. It is a reporting query
that shares no code with the code that decides what plays. The scheduler
itself confirms the setup is right: it checks the schedule window first,
then applies the cadence, and reads times in the station's timezone.
