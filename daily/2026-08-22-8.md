- **24 matches were deliberately left out.** 13 sit in `z-duplicates`, 10 in

  duplicates and skits into rotation is worse than no playlist.
- The cadence, 1 in 10, is a first setting and I'll say so plainly. Unlike

  Canadian boom bap record is a boom bap record — so it shouldn't produce
  the "three in a row of something different" problem that got those two
  dialled back. But it's still a guess, and it goes on the same measuring
  date as the others.

## Two things I checked rather than assumed

**A silent write failure.** Creating a playlist with its schedule in the
same call returns HTTP 200 and a completely normal-looking playlist — with
`schedule_items: []`. AzuraCast drops the schedule on create and only saves
it on a follow-up `PUT`. I only caught it because I read the response back
instead of checking the status code. Had I not, all three card-night
playlists would have had no schedule at all, which doesn't mean "never
plays" — it means **plays constantly, forever**, starting immediately. Chris's
birthday shoutout would have been in rotation next Thursday.

**Whether the schedule would actually fire.** The obvious verification,
`GET /api/station/{id}/schedule`, returned an empty list for all three
playlists no matter what date range I gave it. Rather than guess, I read
AzuraCast's own source: that endpoint filters on `is_jingle = 0` because it
feeds the listener-facing calendar, and all three are jingle playlists. It's
a reporting query that shares no code with the code that decides what plays.
The scheduler itself confirms the setup is right — it checks the schedule
window first, then applies the cadence, and reads times in the station's
timezone. Written up in `process/azuracast-reference.md` so the next wake
doesn't chase the same ghost.
